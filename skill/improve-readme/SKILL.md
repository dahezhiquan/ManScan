# Improve README

完善 `README.md` 时，先从仓库事实出发，再组织成清晰、可执行、对新人友好的中文文档。优先补齐缺失信息，保留已有的项目特有内容，不要把 README 改成空泛模板。

## 强制要求

- 最终生成的 `README.md` 务必使用中文。
- 即使仓库代码、注释、提交记录或现有 README 主要为英文，最终交付的 README 正文仍然使用中文。
- 命令、路径、环境变量、配置键名保持原样；必要时可在中文说明中保留英文技术名词。
- 除非用户明确要求双语或英文版本，否则不要输出英文 README。
- 除了补全内容，还要主动处理基础内容纠错、病句修正、语句润色和 Markdown 排版优化。
- 如果现有 `README.md` 已经有内容且整体结构基本合理，优先做最小必要修改：只修正、删除或补充其中不合理、不准确、过时或缺失的部分，不要为了统一风格而大面积改写原文。
- 最终 README 应兼顾“信息准确”“排版规范”“阅读顺畅”“视觉克制而专业”四个目标。

## 工作流程

### 1. 先读代码和现有文档

- 检查仓库根目录和主要配置文件，例如 `package.json`、`pyproject.toml`、`requirements.txt`、`go.mod`、`Cargo.toml`、`Dockerfile`、`docker-compose.yml`、`.env.example`、`Makefile`、CI 配置。
- 查找现有文档和脚本，例如 `README.md`、`docs/`、`scripts/`、`examples/`、`CONTRIBUTING.md`。
- 从源码目录和启动入口确认项目用途、运行方式、依赖要求和开发约束。
- 只写能从仓库验证出的内容；无法确认时标注“待补充”或给出显式假设。
- 将收集到的事实转换成自然、准确的中文表述，不直接拼接英文句子。
- 同时检查现有 README 是否存在事实错误、过时命令、错别字、重复段落、标题混乱、列表缩进不统一、代码块语言标注缺失等问题。

### 2. 保留真实信息，补齐缺失章节

- 优先增量修改已有 README；不要删除已经准确、有价值的项目背景、截图、架构图或部署说明。
- 如果现有 README 已经符合基本 README 设计，只处理明显有问题的内容；已有且准确的段落、结构和措辞尽量保留，不要无故重排章节或替换整段文字。
- 合并重复内容，把零散说明整理为一套自然的阅读顺序。
- 面向新成员写作：默认读者第一次接触这个仓库，需要从“这是什么”顺畅走到“我怎么跑起来”。
- 章节标题、说明文字、FAQ 结论统一使用中文表达。
- 在不改变仓库气质的前提下，统一 Markdown 风格，提升开源文档阅读体验。

### 3. 至少覆盖这六类内容

一个好的 README 至少应包含以下部分；如果仓库确实不适用，也要明确说明原因而不是直接省略：

1. 项目简介
   说明项目是做什么的、面向谁、解决什么问题。
2. 快速开始
   给出安装依赖、环境配置、启动项目、常见初始化步骤。
3. 技术栈
   列出核心技术、框架、数据库、构建工具，并简述为什么采用它们。
4. 目录结构
   说明主要目录和关键文件的职责。
5. 开发规范
   说明代码风格、分支策略、提交规范、测试要求、Lint/Format 命令。
6. 常见问题
   总结新人最容易卡住的问题、症状、原因和解决办法。

### 4. 同步优化文档表现

- 修正文案问题：错别字、语义重复、语句生硬、英文直译感过强。
- 统一 Markdown 排版：标题层级、列表样式、代码块语言标记、引用块、表格和分隔线用法保持一致。
- 适度加入 Emoji 或装饰元素，帮助读者快速定位章节，但避免堆砌和花哨。
- 调整段落长短、章节顺序和留白，让 README 在 GitHub 等主流开源平台上更易读。

## 章节写法要求

### 项目简介

- 用 2 到 4 句讲清楚项目目标和核心能力。
- 如果仓库偏模板、脚手架、SDK 或内部工具，要写出适用场景，而不是只复述仓库名。

### 快速开始

- 给出可直接复制的命令块。
- 明确前置条件，例如 Node/Python/Java 版本、包管理器、数据库、环境变量。
- 命令顺序按新人第一次运行的真实流程组织。
- 如果存在多种启动方式，先写推荐方式，再写替代方案。
- 对英文命令不要翻译，但要用中文解释每一步是做什么的。

### 技术栈

- 不要只罗列名词；每项尽量补一句职责或选型原因。
- 如果原因无法从仓库中确认，用中性表述，例如“用于统一前端构建流程”。
- 技术名词可以保留英文，但用途说明和选型解释必须写中文。

### 目录结构

- 只解释真正重要的目录，避免把所有文件都列成树。
- 对入口文件、配置目录、业务核心模块优先说明。
- 若项目结构复杂，可同时给出精简目录树和逐项说明。

### 开发规范

- 优先引用仓库已有规则，例如 ESLint、Prettier、ruff、golangci-lint、commitlint、husky、测试命令。
- 如果仓库没有显式规范，不要杜撰团队制度；改写为建议性表达，例如“当前仓库未发现独立提交规范，可沿用 Conventional Commits 作为补充建议”。

### 常见问题

- 问题要具体，优先写真实会卡住新人的地方。
- 推荐格式：问题现象、可能原因、解决步骤。
- 可覆盖依赖安装失败、环境变量缺失、端口占用、数据库未启动、权限不足、构建报错等。

## Markdown 表达规范

### 排版统一

- 标题层级保持稳定，通常使用 `#`、`##`、`###` 即可，避免跳级。
- 相邻章节之间保留清晰留白，不要把长段落堆成“文字墙”。
- 列表项目尽量保持同类句式和相近长度，便于扫读。
- 命令示例、路径、环境变量、文件名、配置键使用代码格式。
- 代码块优先补全语言标记，如 `bash`、`yaml`、`json`、`ts`、`python`。
- 如无必要，不要混用多种列表符号、过多分隔线或复杂 HTML。

### 语句润色

- 先纠错，再润色；不要保留明显病句、错别字或术语混乱。
- 中文表达优先自然、简洁、可执行，避免生硬翻译腔。
- 一段只讲一个核心意思；长句可拆成两到三句。
- 避免空泛口号，优先给出对读者有帮助的说明。

### Emoji 与装饰元素

- 可以为高价值章节智能搭配少量 Emoji，例如：
  - `📦` 项目简介
  - `🚀` 快速开始
  - `🧱` 目录结构
  - `🛠️` 开发规范
  - `❓` 常见问题
- Emoji 的作用是帮助导航，不是装饰密度竞赛；通常二级标题前使用即可。
- 保持整体风格克制、专业，与仓库类型匹配。
- 对偏企业内网、基础设施、底层库项目，可减少 Emoji 使用频率，只在关键章节点缀。

### 开源阅读体验

- 默认 README 会在 GitHub、GitLab 等网页端阅读，优先优化首屏信息密度和章节导航效率。
- 开头应尽快回答“这是什么、适合谁、怎么开始”，不要把重要信息埋在后面。
- 若内容较长，可增加简洁目录或“你可以从这里开始”的导航提示。
- 如果仓库已有徽章、截图、架构图或说明卡片，保留有价值内容，并让其位置服务于阅读顺序。

## 信息不足时的处理

- 先通过代码、配置、脚本和提交痕迹补全事实，不要过早提问。
- 只有在关键信息会直接影响 README 正确性时，才提出 1 个聚焦问题。
- 如果仍然缺信息，保留明确占位，例如“待补充：生产环境部署步骤”。
- 不要编造项目愿景、架构原因、团队流程或运维细节。

## 输出标准

- 标题层级保持简洁，通常使用二级和三级标题即可。
- 语言尽量直接、面向行动，避免营销式空话。
- 命令、环境变量、路径、文件名使用代码格式。
- README 正文、标题、说明、FAQ、目录解释务必使用中文。
- 只有命令、路径、环境变量、配置项、代码符号保留原文，不翻译成中文。
- 交付前检查命令是否前后一致，章节是否完整，术语是否和代码仓库一致。
- 交付前检查 Markdown 是否整洁统一：标题、列表、代码块、段落间距、引用块和表格风格不要互相打架。
- 交付前检查视觉表达是否克制有效：可以更生动，但不要像营销海报或 AI 模板拼贴。

## 推荐产出顺序

1. 先列出拟新增或重写的章节。
2. 再补全可验证的命令、配置和目录说明。
3. 然后统一 Markdown 结构、标题、列表和代码块样式。
4. 最后润色简介、技术栈说明、FAQ 和整体视觉节奏。
