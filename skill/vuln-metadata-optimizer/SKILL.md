# 漏洞元信息优化

当用户要求改进、补充、汉化或审查漏洞模板 `info` 块中的元信息时使用本 skill，重点覆盖 `description`、`impact`、`remediation`、`classification` 和 `metadata`。

## 资料获取要求

1. 先阅读目标模板，包括 `info.reference`、`classification`、`metadata`，以及请求路径、参数、匹配器、提取器、DSL 条件、payload、OAST/OOB 用法等 POC 检测逻辑。
2. 对所有可能描述该漏洞的公开参考链接，必须先使用 `vuln-page-extractor` skill 获取结构化漏洞信息。优先依据其输出的字段和证据片段，不要仅凭记忆改写。
3. 如果 `vuln-page-extractor` 无法获取足够有效的漏洞信息，再联网搜索该漏洞、CVE、产品公告、利用分析、补丁说明或厂商通告。优先使用厂商公告、CNA/NVD 记录、官方发布说明、修复提交和可信技术分析。
4. 如果可靠来源仍无法支撑某个字段，保持原字段不变或不新增该值。不要编造影响范围、修复方式、CWE、CVSS、厂商或产品信息。

## 字段规则

- `description`：存在时进行优化；只有用户要求补全或新增元信息时才新增。内容必须使用中文展示，除非涉及专有名称、漏洞编号、协议名、参数名、路径、代码或匹配关键字。应简洁覆盖三部分：
  - 漏洞简介：受影响产品或组件、漏洞类型、攻击前提和主要后果。
  - 漏洞原理：结合公告、补丁或 POC 说明成因，不要超出证据。
  - POC 检测方法：简要描述模板如何验证漏洞，参考请求路径、参数、匹配器、回显、时间差、OAST/OOB 或状态码等检测证据；不要写成可直接武器化的利用教程。
- `impact`：存在时进行优化；只有用户要求补全或新增元信息时才新增。内容必须使用中文展示，除非涉及专有名称、代码或必要技术术语。应从真实部署环境说明实际安全影响，例如数据泄露、权限边界绕过、服务接管、横向移动、持久化、业务中断或需要用户交互的攻击链。避免“存在安全风险”“影响较大”等泛泛表达。
- `remediation`：存在时进行优化；只有用户要求补全或新增元信息时才新增。内容必须使用中文展示，除非涉及专有名称、版本号、配置项、命令、代码或路径。应给出有来源支撑的明确修复方式，例如修复版本、补丁名称、配置调整、禁用暴露功能、访问控制、输入校验、输出编码、凭据轮换或临时缓解措施。若同时存在厂商修复和补偿性控制，应区分说明。
- `classification`：当可靠来源提供 `cve-id`、`cwe-id`、`cvss-score` 时进行补充。保持其与模板 ID 和严重等级一致。若多个 CVSS 分数冲突，厂商或 CNA 分数明显权威时优先采用；否则采用 NVD，并在总结中说明不确定性，不要强行填入冲突值。
- `metadata`：当受影响厂商或组件明确时补充 `vendor` 和 `product`。除非仓库已有其他明确约定，否则使用小写 slug 风格。

## 厂商和产品归一化

新增或修改 `metadata.vendor`、`metadata.product` 前，必须先在已有模板中搜索等价表达和产品命名：

- 搜索 `metadata.vendor`、`metadata.product`、`tags`、`id` 和 `info.name`。
- 如果同一厂商或产品在仓库中已有稳定写法，应复用已有写法。
- 同一实体应尽量只保留一个规范值，不要为同一厂商制造 `apache`、`apache-software-foundation`、`apachefoundation` 这类并行变体。
- 如果已有模板存在冲突，选择与受影响产品匹配且出现更频繁的表达，并在最终总结中说明归一化选择。

## 编辑限制

- 尽量保持模板原有结构、缩进、字段顺序和 YAML 风格。
- 修改范围应限制在用户要求的元信息内。除非用户明确要求，不要改动请求、匹配器、payload、变量、flow 或协议块。
- 补充或优化后的内容应以中文展示，除非内容是专有名称、产品名、厂商名、漏洞编号、协议名、路径、参数、配置项、代码、命令或必要技术术语。
- 中文应专业、具体，适合直接作为漏洞模板元信息使用。
- `impact` 或 `remediation` 包含多条内容时，使用 Markdown `- ` 列表。
- 不要在中文元信息中残留完整英文句子，除非它本身是必须保留的产品名称、漏洞编号、协议名称、代码或技术术语。
